# Azure DevOps PR Review for OpenCode — 0.5.1

This release moves the tested host to OpenCode 2.4.1 and fixes what OpenCode
2.3.1 to 2.4.1 change for AZPR, together with defects that were there before.
The prompt files are those of 0.5.0, no setting is new, and your settings
and saved reviews are used as they are.

**If you run OpenCode 2.4.0 or 2.4.1 with AZPR 0.5.0 and use the terminal
panel, upgrade AZPR.** There, a step of the panel that was pressed and not
released can be picked by a later click somewhere else, and with **Post N
comments…** that can post comments nobody asked for (the first item below).
Until you have upgraded, do not hold the mouse button down on a step; typed
commands and the panel's keys are not affected.

## What changed

- **A release the terminal UI makes up no longer picks a step.** OpenCode
  2.4.0 and later end a mouse drag whose release they never saw (the pointer
  left the window with the button down, for instance) at the next press of
  the button, anywhere and any time later, with a release for the element
  that was pressed first. 0.5.0 took that for a click. In a fixture, with the
  step **Post 3 comments…** and the next click where the question's "Yes" row
  appears, the three comments were posted. A release now counts as a click
  only within a second of the pointer's last movement with the button down; a
  button held still is a click for any time. The rows of the sessions and
  `close` follow the same rule. A release the terminal UI makes up within
  that second is still taken for a click (see the known limitations below).
  OpenCode 2.3.x makes no such release up.
- **Local instructions stay out of private sessions.** OpenCode adds to every
  request what it collects for the conversation's directory: `AGENTS.md`
  (from 2.3.1 also `CLAUDE.md` and `~/.claude/CLAUDE.md`), the instruction
  files a configuration lists, and what MCP servers, references and skills
  say of themselves. All of it went to every reviewer, duplicate check,
  rating and comment planning session, although it describes your local
  directory and not the PR: with an instruction file of 54,000 characters,
  the system messages of a small review and its preview grew from 138,000 to
  625,000 characters. Private sessions now get AZPR's own instructions and
  OpenCode's date and environment, also with `claude-agent` models (for one
  note that still does not reach those models, see the known limitations).
  Your own conversations are not touched. A reviewer can still read local files on
  purpose. Where AZPR cannot tell these parts of a request apart (another
  plugin rewrote them, or a later OpenCode builds them another way), it sends
  them as it received them, as 0.5.0 did, and the stage's debug record
  counts the request.
- **Reading a file beside a nested instruction file no longer fails the
  pass.** When a reviewer's native `read` reads a file of the local project
  in a directory that has an `AGENTS.md` of its own (from OpenCode 2.3.1 also
  a `CLAUDE.md`), OpenCode leaves that file in the session. 0.5.0 took it for
  someone else's message and failed the pass, and its retry too. Such a
  message is now kept from the model and ends no turn.
- **Rows that OpenCode's read returns whole.** A value too large for a prompt
  (a long PR description, the file list of a large PR, a large tool result)
  is handed to a model as a reference to pages, which it reads with OpenCode's
  native read. That tool cuts every line after 2,000 characters, and a row
  held up to 3,000, so a model got about two thirds of what it read. Rows now
  fit, and a saved review gets pages that fit, beside its own, whenever it
  is used. A review that 0.5.1 saved can still be commented on after going
  back to 0.5.0 as far as the rows of its values are there under the earlier
  name as well: 0.5.1 leaves them there as hard links where it can, which is
  not on a file system without hard links and not where something else has
  that name. Where they are missing, run the review again after going back.
- **A usage limit that a ChatGPT workspace's admin set is named and not
  retried.** OpenCode 2.4.0 reports it as a type of its own, which 0.5.0 did
  not know: a stage that hit it started a second session that failed the same
  way, and the receipt said only HTTP 429.
- **One of AZPR's commands that arrives as an ordinary prompt is stopped.**
  `opencode --prompt "/pr-review …"` can submit the text before the terminal
  UI has loaded the commands. With OpenCode 2.4.0 and 2.4.1 that happened in
  14 of 16 starts in a fixture, and in 10 of them the conversation ran on
  OpenCode's built-in free model, which would have been sent the PR URL and
  your context. Where AZPR's settings are in use, it now refuses a prompt of
  an ordinary conversation that begins with one of its commands, before any
  model gets it, and says so there (a process without usable settings, as
  before a first setup, has no such hook). The terminal UI then reports a
  session that failed and may try again
  in new conversations, which stay empty. Start commands in the terminal UI
  once they are listed, or from a script with the command endpoint.
- **With shell allowed, a command that goes on in the background no longer
  fails its pass.** From OpenCode 2.3.1 a reviewer's command that outlasts its
  timeout, 120 seconds by default, is moved to the background, and OpenCode
  tells the session when it has ended. 0.5.0 took that notice for someone
  else's message: the pass failed, and its retry ran the command again. A
  command that ends while the session is still at work, also right after its
  answer, is handed to the model in the same turn, which may answer once
  more. One that ends after the session has gone idle wakes the session,
  which then gets no model request and no tool, and the answer stands. This
  concerns `shell: "ask"` and `"inherit"` only; the default is `"deny"`.
- **A review's receipt lists the stages in one order**: the passes in their
  order, the duplicate checks, the rating. The report is in the session of the
  last of them that did not fail. Until now both followed the order in which
  OpenCode had created the sessions, which differed between runs of one
  review.
- AZPR's tool definitions are no longer part of the requests OpenCode builds
  for your own conversations outside a turn (a summary, also the one it writes
  in the background, and a side question): six definitions that those
  sessions could never call.

The documentation is corrected in two places. With `claude-agent` models, a
session's local process ends five minutes after the session's last turn, not
when OpenCode exits, and OpenCode 2.4.0 and later end it when the session is
deleted; Claude Code also keeps a transcript of every such session under its
own configuration directory, which deleting the OpenCode session does not
remove. And OpenCode writes background summaries by default from 2.3.1 on,
not from 2.3.2.

## Upgrading OpenCode

Upgrade AZPR first, then OpenCode. 0.5.1 also runs on OpenCode 2.3.0 to
2.4.0, where `/pr-check` shows the OpenCode WARNING row. Choose 2.4.1 over
2.4.0: 2.4.0 cannot save an assistant's answer on macOS 12.

Back up OpenCode's database before the upgrade. OpenCode 2.3.1 and 2.4.0 add
migrations, and 2.4.0 stores an answer's parts in rows of their own, so going
back to an earlier OpenCode needs the backup. Close every OpenCode that uses
the database first: the commands below stop the background service, but a
terminal UI or an `opencode serve` that you started yourself writes to the
same database, and files copied while one of them writes may not fit
together.

```sh
data="${XDG_DATA_HOME:-$HOME/.local/share}/opencode" &&
  backup=~/opencode-db-backup-$(date +%Y%m%d-%H%M%S) &&
  test -f "$data/opencode.db" &&
  mkdir -m 700 "$backup" &&
  opencode service stop &&
  cp -p "$data/opencode.db" "$backup"/ &&
  { test ! -e "$data/opencode.db-wal" || cp -p "$data/opencode.db-wal" "$backup"/; } &&
  { test ! -e "$data/opencode.db-shm" || cp -p "$data/opencode.db-shm" "$backup"/; } &&
  npm install -g @opencode/cli@2.4.1 &&
  opencode service start &&
  echo "Database as it was before the upgrade: $backup"
```

Each step runs only when the one before it succeeded, so OpenCode is not
upgraded without its backup, and nothing is changed when no database is found
where OpenCode keeps it by default. Only the database and the two files SQLite
keeps beside it are copied, not whatever else has a name that begins like
theirs. Every run makes a directory of its own, readable by you alone, so this
backup is never mixed with an earlier one and never replaces it; the last line
says where it is. Use `sudo` for the global install if your npm prefix needs
it. If a step fails after the service was stopped (a copy, the install), the
service is still stopped: start it with `opencode service start`.

To go back to the earlier OpenCode, the backup takes the place of the
database, and what was done since the upgrade (every conversation of that
time, not only reviews) is not in it. So the database of that time is moved
aside, into a directory of its own that only you can read, and nothing is
deleted. Close every OpenCode first, as for the upgrade; put the directory the
upgrade named and the version you go back to in the first two lines:

```sh
backup=~/opencode-db-backup-YYYYMMDD-HHMMSS
version=2.3.2
data="${XDG_DATA_HOME:-$HOME/.local/share}/opencode" &&
  since=~/opencode-db-since-upgrade-$(date +%Y%m%d-%H%M%S) &&
  test -f "$backup/opencode.db" &&
  mkdir -m 700 "$since" &&
  opencode service stop &&
  npm install -g "@opencode/cli@$version" &&
  { test ! -e "$data/opencode.db" || mv "$data/opencode.db" "$since"/; } &&
  { test ! -e "$data/opencode.db-wal" || mv "$data/opencode.db-wal" "$since"/; } &&
  { test ! -e "$data/opencode.db-shm" || mv "$data/opencode.db-shm" "$since"/; } &&
  cp -p "$backup/opencode.db" "$data"/ &&
  { test ! -e "$backup/opencode.db-wal" || cp -p "$backup/opencode.db-wal" "$data"/; } &&
  { test ! -e "$backup/opencode.db-shm" || cp -p "$backup/opencode.db-shm" "$data"/; } &&
  opencode service start &&
  echo "Database as it was since the upgrade: $since"
```

Nothing is changed when the backup is not where the first line says. The
files SQLite keeps beside the database are moved with it: one of the newer
database left beside the restored one would be applied to it. If a step
fails, nothing is lost: the backup stays where it was, what was moved is in
the directory the command made (`~/opencode-db-since-upgrade-…`), and the
service is still stopped. Keep that directory until you know you will not
want what it holds.

Two things are new with OpenCode 2.4.x and are now in the
[README](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.1/README.md#native-package-npm-or-git):

- **Keep the exact version in the plugin entry.** OpenCode 2.4.0 and later
  update an entry that follows a version by themselves (`…@latest`, a range, a
  Git branch), when the service starts and every 24 hours, and load the new
  version at once, which ends a review that is running. An exact version and
  a Git tag are never changed that way.
- **List AZPR first.** OpenCode loads AZPR again whenever a plugin that is
  loaded before it changes, another plugin's automatic update included.
  Local plugins in the configuration directory's `plugin/` and `plugins/`
  folders are loaded first, then the entries of the `plugins` list in their
  order.

## Installation

```sh
opencode plugin add opencode-azure-devops-pr-review@0.5.1
```

Alternatively, install the same release from Git:

```sh
opencode plugin add 'github:WTLAIB/opencode-azure-devops-pr-review-v2#v0.5.1'
```

Add only one of them. Then open OpenCode's terminal UI and type `/pr-setup`;
the
[quickstart](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.1/docs/QUICKSTART.md)
walks through it and shows the way without the terminal UI.

## Upgrading AZPR

For an entry that `opencode plugin add` created, add 0.5.1 and remove the
previous version only when the download succeeded. Replace `PREVIOUS_VERSION`
with the version in your `plugins` entry, such as 0.5.0:

```sh
opencode plugin add opencode-azure-devops-pr-review@0.5.1 &&
  opencode plugin remove opencode-azure-devops-pr-review@PREVIOUS_VERSION
```

Run them when no AZPR command is running. Running only the first command
leaves the previous version running. For an entry with options, change only
its `package` value. See
[upgrading](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.1/README.md#upgrading)
for the details. Settings, the PAT file and review records remain in place,
and no setting is new or required. Coming from 0.4.x, the settings need the
update that the
[0.5.0 release notes](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.1/docs/releases/v0.5.0.md)
describe.

For a source installation, extract the new archive and run its installer with
`--replace` to retain settings:

```sh
sh install.sh --config-dir /absolute/path/to/v2-opencode-config --replace
```

Manual copying needs the same 33 files as 0.5.0.

## Known limitations

Not changed by this release:

- A reviewer's answer that reaches the model's output limit fails its pass,
  and the receipt names another message in the turn, not the limit. Lower
  `workflow.shardFiles` or use a model with a larger output limit.
- In the list that adjusts findings, typing an ID selects by OpenCode's fuzzy
  search: with ten or more findings, `F-1` selects `F-11`. The dialog that
  opens names the finding in its title; read it before choosing.
- Page Up and Page Down close the token dialog of `/pr-setup`, as they close
  OpenCode's own dialogs; nothing is saved then.
- With `claude-agent` models, the note that AZPR adds to a comment planning
  session that has read much ("Finish this work page now…") does not reach
  the model: OpenCode's Claude Code provider does not send what a plugin adds
  to a request's system parts. The planner then loses its tools for that
  request without being told why, as in 0.5.0.
- Several OpenCode processes share AZPR's state directory, and each knows
  only its own running commands: one that saves a twenty-first review can
  remove the oldest saved review while another process is planning or
  posting its comments, and a process that starts can remove the data of
  another process's run that has gone on for more than a day. That command
  then fails, as in every version so far.
- After a release was lost, a second press within a second of the pointer's
  last movement can still pick the step that was pressed. The second is
  measured where the terminal UI handles the two events, which carry no time
  of their own: where its input waited meanwhile (the program was stopped, or
  the machine was busy for that long), a press made later counts the same.
- The other side of that rule: a step, a session's row or `close` that is
  pressed, moved on a little and released more than a second after the last
  movement is not taken; click again. This holds on OpenCode 2.3.x too, which
  makes no release up: the terminal part cannot tell which OpenCode it runs
  in on those versions, and it does not guess.

## Compatibility and validation

The tested target is OpenCode CLI **2.4.1** (V2 plugin API), Node.js
**22.23.3**, Ubuntu **22.04.5** under WSL2, and Azure DevOps Services REST API
**7.1**. `/pr-check` warns on other OpenCode versions. OpenCode 1.x and Azure
DevOps Server are not supported; other operating systems remain unvalidated.

The prompt files under `src/prompts` are unchanged. What a private session is
sent besides them changed, as described above, and a pass that a nested
instruction file used to fail now completes. The
[validation record](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.1/docs/VALIDATION.md#051-release-candidate-acceptance-2026-11-26)
lists the offline checks and the checks on a real OpenCode 2.4.1 host with
fake services, and the
[comparison of OpenCode 2.3.1 to 2.4.1 with 2.3.0](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.1/docs/VALIDATION.md#opencode-231-to-241-compared-with-230-2026-11-24-to-26)
says what was measured on which version and what was only read from
OpenCode's source. No review with a real model was run on this candidate.

The npm package, Git package and source archive contain the same runtime, with
no npm dependencies or install scripts; the source archive also contains the
documentation, installers and settings example. The release source artifact is
`opencode-azure-devops-pr-review-v2-0.5.1.tar.gz`, with checksums in `SHA256SUMS`.
