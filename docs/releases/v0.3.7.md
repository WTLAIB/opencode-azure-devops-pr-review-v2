# Azure DevOps PR Review for OpenCode — 0.3.7

This release changes how a finding's severity is set. Severity decides where a
finding appears: high and medium findings get an inline comment, low findings
appear only in the summary. A change that breaks what worked before is now at
least medium, the verifier sets each level from what it verified without
seeing the reviewer's label, and an optional rating model can set the final
levels. A few rules about what a finding states are tighter. Commands, comment
previews, adjustments and publication work as in 0.3.6, and the tested host
stays OpenCode 2.2.4.

## What changed

- **Regressions are at least medium.** A change that breaks something the base
  commit handled (an input, configuration or call that now fails or gives a
  wrong result) is at least medium, however rarely it is used. Documented steps
  that worked before the change and fail after it count too, even though the
  failure shows at once, and a question about intent is medium instead of low
  when the behavior stops something that worked. An easy fix and an effect the
  reviewer could not confirm no longer lower a level.
- **The verifier sets severity itself.** Candidates reach the verifier without
  the reviewer's severity, so it rates each finding from the harm and trigger
  it verified instead of keeping a label. Without a rating model that level is
  final.
- **Optional severity rating.** `models.review.rater` and `models.deep.rater`
  name a model for a new stage: after verification, a session without tools
  rates the confirmed findings from their text alone, 25 at a time, and its
  level is final. A finding it does not rate keeps the verifier's severity.
  Left out or empty, which is the default, the stage does not run. It is meant
  for a rater stronger than the reviewers' model; see the measurements below.
- **One defect per finding.** A second defect a reviewer notices on the way is
  filed on its own, a wrong test is stated as what it wrongly accepts, and a
  merge in verification no longer drops a defect that only the merged finding
  named.
- **Questions about intent.** Before asking whether the author meant a
  behavior, a reviewer looks for a statement of that intent in the tests, the
  comments and documents beside the code, the PR description and the commit
  messages. NEEDS_INFO is for behavior the verifier could not establish: a
  verified behavior that only the author, or a specification outside the
  repository, can call intended is confirmed as a question to the author.
- **One more read.** A reviewer makes the read that would settle a suspicion
  before answering.

`/pr-review` and `/pr-deep` work this way. `/pr-quick` follows the same
reviewer rules and keeps its flow: one reviewer per shard, no verifier and no
rating, with the reviewer's severity.

## Measured effect

In the 0.3.6 measurement on the 25 pull requests of the public
[ReviewBench](https://github.com/review-bench/ReviewBench) test set, `/pr-deep`
with Claude Opus 5.5 had labeled low 96 of the 190 findings that ReviewBench's
judge rated medium or high, so they appeared only in the summary. The
instructions and runtime of this release reviewed the same pull requests once,
with the same setup, through a local fixture of the Azure DevOps API:

| `/pr-deep`, Claude Opus 5.5 | Findings | High | Medium | Low | Inline comment |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 0.3.6 | 283 | 19 | 83 | 181 | 36% |
| 0.3.7 | 269 | 18 | 117 | 134 | 50% |

ReviewBench's judge did not score the new run. To compare the labels anyway,
each finding of the new run was paired, by its location and wording, with a
finding of the 0.3.6 run that the judge had rated valid. 204 findings have
such a partner and take its judged level. Of the 153 that the judge had rated
medium or high, the 0.3.6 run labeled 67 low (43.8%) and the 0.3.7 run 45
(29.4%). Agreement with the judge on which of the 204 deserve
an inline comment rose from an F1 of 71.7 to 81.2: recall rose from 56.2% to
70.6% and precision fell from 98.9% to 95.6%.

The same run also used the optional rating, with Claude Opus 5.5 as the rater.
It changed 46 levels and added 1.7 points to that F1, less than the 5 points
set in advance for recommending a rater of the reviewers' own model. With
GPT-6.1 Sol rating its own review on an earlier build of this change, the
rating and the verifier agreed on the inline decision for 318 of 333 findings.
The rating is therefore off unless you name a rater. Recall and the share of
valid findings were not measured again with ReviewBench's judge for this
release. The
[validation record](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.3.7/docs/VALIDATION.md#severity-from-verified-harm-2026-11-11-and-12)
describes the runs, the pairing and the limits.

## Installation

```sh
opencode plugin add opencode-azure-devops-pr-review@0.3.7
```

Alternatively, install the same release from Git:

```sh
opencode plugin add 'github:WTLAIB/opencode-azure-devops-pr-review-v2#v0.3.7'
```

Add only one of them. Follow the
[quickstart](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.3.7/docs/QUICKSTART.md)
for a private PAT file, `/pr-setup`, a service restart and the first review.

## Upgrading AZPR

For an entry that `opencode plugin add` created, add 0.3.7 and remove the
previous version only when the download succeeded. Replace `PREVIOUS_VERSION`
with the version in your `plugins` entry, such as 0.3.6:

```sh
opencode plugin add opencode-azure-devops-pr-review@0.3.7 &&
  opencode plugin remove opencode-azure-devops-pr-review@PREVIOUS_VERSION
```

Run them when no AZPR command is running: OpenCode 2.2.4 switches the running
service to 0.3.7 within seconds, without a restart, and
`opencode plugin list` should then show a single `azpr` row with 0.3.7. Running
only the first command leaves the previous version running. For an entry with
options, change only its `package` value; the OpenCode service then downloads
0.3.7 with its own network settings. See
[upgrading](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.3.7/README.md#upgrading)
for the details. External settings, the PAT file and review records remain in
place. This release adds one optional setting, `rater` under `models.review`
and `models.deep`, and no required migration: settings without it work as
before and run no rating. Reviews saved by 0.3.6 keep their findings and
severities; only new reviews use the new rules.

For a source installation, extract the new archive and run its installer with
`--replace` to retain settings:

```sh
sh install.sh --config-dir /absolute/path/to/v2-opencode-config --replace
```

The installer adds the empty `rater` entries to `settings.json` and changes
nothing else in it. Manual copying needs one more file,
`src/prompts/rating.md`.

## Compatibility and validation

The tested target is OpenCode CLI **2.2.4** (V2 plugin API), Node.js
**22.23.3**, Ubuntu **22.04.5** under WSL2, and Azure DevOps Services REST API
**7.1**. OpenCode 1.x and Azure DevOps Server are not supported; other operating
systems remain unvalidated.

The reviewer and verifier instructions changed (`src/prompts/common.md` and
`src/prompts/final.md`), the rating has its own (`src/prompts/rating.md`), and
the runtime gained the optional stage. Without a rater a review runs the same
stages as in 0.3.6. The
[validation record](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.3.7/docs/VALIDATION.md)
lists the offline and real-host checks with fake services and the runs above.
A live review of the candidate with `openai/gpt-6-luna` on the 1-file test PR,
in a service on OpenCode 2.2.4 with settings written by 0.3.6, completed and
confirmed the PR's three known defects; its comment preview was not published.

The npm package, Git package and source archive contain the same runtime, with
no npm dependencies or install scripts; the source archive also contains the
documentation, installers and settings example. The release source artifact is
`opencode-azure-devops-pr-review-v2-0.3.7.tar.gz`, with checksums in `SHA256SUMS`.
