# Azure DevOps PR Review for OpenCode — 0.3.5

This release changes how reviewers set severity. A finding's severity now says
how much it matters to fix it before the change merges, judged from the harm
the evidence shows and how often realistic use reaches it. Settings, commands,
comment previews, adjustments and publication work as in 0.3.4, and the tested
host stays OpenCode 2.2.4.

## What changed

- **Severity says how much fixing matters before the merge.**
  - **high** (must fix before merging): realistic use leaves a core function
    or what the change is for not working, or causes serious harm: a security
    breach, data people keep lost, corrupted or exposed, or results people act
    on that are silently wrong.
  - **medium** (should fix in this change): realistic use hits a failure that
    people notice and recover from, such as an error or wrong result for some
    valid inputs, a broken secondary path or a failing test or build, or a rare
    trigger causes serious harm.
  - **low** (can wait): anything else, such as a recoverable failure that only
    a rare trigger reaches, or a finding with no effect on behavior
    (duplication, naming, a stale comment, a missing test for working code).

  Reviewers judge severity from the harm their evidence shows and how often
  realistic use reaches it, not from their confidence, the size of the fix or
  the kind of issue. Realistic use means ordinary inputs, common
  configurations and deployments, failures that dependencies routinely produce
  (a dropped connection, an error from a remote service), concurrent use where
  the code runs concurrently and, at a security boundary, anyone who can reach
  it. A rare trigger lowers a finding's severity; it does not keep a defect out
  of the findings.
- **Gaps are rated by their effect.** In 0.3.4 concrete gaps were usually low.
  Now a document or example is rated by what following it does, shipped
  configuration like code, and a missing or ineffective test is low unless the
  test is what the change delivers. When a missing test hides a defect in the
  change, the defect is reported with its own severity, and its suggested fix
  names the test that would catch it.
- **The verifier sets the final severity.** It sets each confirmed finding's
  severity from the harm and trigger it verified: the reviewer's severity is a
  claim like the rest, raised or lowered as the evidence requires, with the
  reason. `/pr-quick` reviewers use the same scale for their own checks.
- **Each rule is stated once.** The reviewer instructions no longer repeat
  shared rules in the role prompts, and the shared tool guidance leaves what
  each tool returns to the tools' own descriptions.

Publication is unchanged: inline comments go to high and medium findings, and
low findings stay in the summary index. With gpt-6.1-sol, reviews label many
more findings high and slightly fewer low, so slightly more findings get an
inline comment. `/pr-review`, `/pr-deep` and `/pr-quick` share these rules.

## Measured effect

Before release, the new instructions were compared with those of 0.3.4 on the
public [ReviewBench](https://github.com/review-bench/ReviewBench) test set,
served to OpenCode 2.2.4 through a local fixture of the Azure DevOps API and
scored with the benchmark's matcher and classifier rubric by Claude Opus
subagents rather than its official judge. Each finding's severity was compared
with the severity the judges gave the same issue, and two runs of the same
instructions measured how much results vary between runs. The comparison shows
the direction of the change, not a leaderboard result:

- With `/pr-deep` and gpt-6.1-sol, many more of the issues the judges rated
  high were labeled high, while the share of high labels that the judges also
  rated high stayed about the same. Fewer findings that deserve an inline
  comment were labeled low.
- What reviews found and the share of findings judged valid stayed within the
  variation between runs, and so did the final step that states each rule
  once.
- With `/pr-review` and gpt-6-luna, results stayed within the variation between
  runs, which is large for this model.

The
[validation record](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.3.5/docs/VALIDATION.md)
describes the method and its limits.

## Installation

```sh
opencode plugin add opencode-azure-devops-pr-review@0.3.5
```

Alternatively, install the same release from Git:

```sh
opencode plugin add 'github:WTLAIB/opencode-azure-devops-pr-review-v2#v0.3.5'
```

Add only one of them. Follow the
[quickstart](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.3.5/docs/QUICKSTART.md)
for a private PAT file, `/pr-setup`, a service restart and the first review.

## Upgrading AZPR

For an entry that `opencode plugin add` created, add 0.3.5 and remove the
previous version only when the download succeeded. Replace `PREVIOUS_VERSION`
with the version in your `plugins` entry, such as 0.3.4:

```sh
opencode plugin add opencode-azure-devops-pr-review@0.3.5 &&
  opencode plugin remove opencode-azure-devops-pr-review@PREVIOUS_VERSION
```

Run them when no AZPR command is running: OpenCode 2.2.4 switches the running
service to 0.3.5 within seconds, without a restart, and
`opencode plugin list` should then show a single `azpr` row with 0.3.5. Running
only the first command leaves the previous version running. For an entry with
options, change only its `package` value; the OpenCode service then downloads
0.3.5 with its own network settings. See
[upgrading](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.3.5/README.md#upgrading)
for the details. External settings, the PAT file and review records remain in
place, and this release adds no settings or required migration. Reviews saved
by 0.3.4 keep their severities; only new reviews use the new scale.

For a source installation, extract the new archive and run its installer with
`--replace` to retain settings:

```sh
sh install.sh --config-dir /absolute/path/to/v2-opencode-config --replace
```

## Compatibility and validation

The tested target is OpenCode CLI **2.2.4** (V2 plugin API), Node.js
**22.23.3**, Ubuntu **22.04.5** under WSL2, and Azure DevOps Services REST API
**7.1**. OpenCode 1.x and Azure DevOps Server are not supported; other operating
systems remain unvalidated.

Only the reviewer instructions changed: the prompt files and the shared tool
guidance in `src/config.mjs`. The runtime logic is that of 0.3.4. The
[validation record](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.3.5/docs/VALIDATION.md)
lists the offline and real-host checks with fake services and the comparison
above. A live review of the candidate with `openai/gpt-6-luna` on the 1-file
test PR, in a service on OpenCode 2.2.4, completed and confirmed the PR's three
known defects; its comment preview was not published.

The npm package, Git package and source archive contain the same runtime, with
no npm dependencies or install scripts; the source archive also contains the
documentation, installers and settings example. The release source artifact is
`opencode-azure-devops-pr-review-v2-0.3.5.tar.gz`, with checksums in `SHA256SUMS`.
