# Azure DevOps PR Review for OpenCode — 0.5.0

Every review now runs one pipeline: independent review passes, a duplicate
check and a severity rating, then comment planning as before. `/pr-review`,
`/pr-deep` and `/pr-quick` differ only in the models you list for them. The
verifier is gone, and so is the split into a functional and a risk reviewer.

This release changes how findings are produced, what reports and comments say
about them, and the layout of the settings file. **Settings of 0.4.x are not
used until you confirm an update that `/pr-setup` shows first**; read
"Upgrading from 0.4.x" below before you install.

## What changed

- **Passes instead of roles.** A mode's models are a list, and each entry is
  one pass: an independent reviewer session per shard that covers function and
  failure behaviour, reads beyond the diff, and checks each of its findings
  against the source before it answers. Passes do not see each other's work.

  ```json
  "models": {
    "review": { "reviewers": ["provider/model-a", "provider/model-a"], "rater": "" },
    "deep":   { "reviewers": [], "rater": "" },
    "quick":  { "reviewers": ["provider/model-a"], "rater": "" }
  }
  ```

  One to four entries; an entry may repeat, and entries may be different
  models. An empty list leaves `/pr-deep` or `/pr-quick` off. No mode falls
  back to another mode's models.
- **No verifier.** Nothing checks a finding after its reviewer. The runtime
  checks what it can check without judging: every field is there, the location
  exists at the reviewed commit, and the session that reports a finding read
  that file. Findings that pass are `REPORTED`; the others are `NEEDS_INFO` and
  are never commented on. Reports, receipts and posted comments say that no
  separate verification ran.
- **A duplicate check across sessions.** Where different reviewer sessions
  reported findings in one file, a session of the first reviewer model compares
  them and merges repeated reports of one defect: the same root cause and the
  same correction. The same kind of mistake at several places stays several
  findings (one comment may still cover them, as since 0.4.6). Two findings of
  one session are never merged, and a check that fails keeps every finding.
- **A severity rating, on by default.** Sessions without tools then rate the
  reported findings from their text alone, without the level their reviewer
  gave them, so that the findings of different models stand on one scale.
  `rater` is `""` (the first reviewer model rates), a model, or `false` (no
  rating: the reviewers' levels stay). The report shows the reviewer's own
  level where the rating changed it. In 0.4.x the rating ran only with a named
  rater.
- **Finding IDs are `F-1`, `F-2`, … for the whole review**, numbered by place
  and then by pass. They no longer say which reviewer found something.
- **Coverage is two numbers** when a mode has several passes: the changed
  files reviewed in at least one pass, and those reviewed in every pass. A pass
  that fails costs depth, which the second number and a warning show.
- **Comments say how the review was made.** New comments end with "Review
  method: findings checked by their reviewer against the source, no separate
  verification" and the models. Comments that are already on a pull request
  keep their line, and AZPR recognises them as its own.

Comment planning, previews, adjustments (`--exclude`, `--severity`),
automatic comments and publication work as before; the first reviewer model
plans the comments. Reviews that 0.4.x saved can still be shown, previewed and
published.

## Choosing models

- Start with one model. `/pr-setup` writes it twice for `/pr-review` (two
  passes) and once for `/pr-quick`.
- With models of two vendors, one pass each found more than two passes of one
  model in our runs, at the same share of valid findings.
- The first entry of a list also checks duplicates and plans the comments,
  and rates the severities unless `rater` names another model. Put a model
  whose severity levels you trust first, or name a `rater`.
- `/pr-deep` is the same review with stronger models, a higher variant
  (`provider/model#high`) or more passes, for the pull requests that need it.
- More passes run side by side, so they mainly cost more. With
  `claude-agent` models on OpenCode 2.3.2, every session keeps a local process
  until OpenCode exits: many passes over many shards need memory.

What was measured, with which judge, and what was not is in the
[validation record](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.0/docs/VALIDATION.md#one-pipeline-passes-instead-of-roles-2026-11-22-and-23).
The benchmark results in the README were measured with 0.3.5 to 0.4.6 and are
labelled so; 0.5.0 has not been scored by those benchmarks' own judges yet.

## Installation

```sh
opencode plugin add opencode-azure-devops-pr-review@0.5.0
```

Alternatively, install the same release from Git:

```sh
opencode plugin add 'github:WTLAIB/opencode-azure-devops-pr-review-v2#v0.5.0'
```

Add only one of them. Then open OpenCode's terminal UI and type `/pr-setup`;
the
[quickstart](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.0/docs/QUICKSTART.md)
walks through it and shows the way without the terminal UI.

## Upgrading from 0.4.x

For an entry that `opencode plugin add` created, add 0.5.0 and remove the
previous version only when the download succeeded. Replace `PREVIOUS_VERSION`
with the version in your `plugins` entry, such as 0.4.6:

```sh
opencode plugin add opencode-azure-devops-pr-review@0.5.0 &&
  opencode plugin remove opencode-azure-devops-pr-review@PREVIOUS_VERSION
```

Run them when no AZPR command is running. Running only the first command
leaves the previous version running. For an entry with options, change only
its `package` value. See
[upgrading](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.0/README.md#upgrading)
for the details. The PAT file and review records remain in place.

Then update the settings:

1. After the restart, AZPR's commands only say that the settings need an
   update. Your settings file is untouched, and no review or Azure request
   starts.
2. Run `/pr-setup`. It shows what the update changes: for each mode the models
   it had and the passes it gets, what happens to the rating, and anything
   else that will behave differently.
3. Confirm. In OpenCode's terminal UI, `/pr-setup` asks in a list whose first
   row keeps the file as it is. In other clients it prints the command that
   confirms the change it showed:

   ```text
   /pr-setup --migrate <word>
   ```

   The word belongs to the file as it was shown; if the file changed
   meanwhile, `/pr-setup` shows the update again. The update is loaded at
   once; `/pr-check` then shows each mode's passes.

What the update does:

- The functional and the risk model of `/pr-review` (and of `/pr-deep`)
  become that mode's two passes, in that order. The verifier model is dropped.
- A quick reviewer becomes a list of one.
- A named rater stays. A mode without one now has its findings rated by its
  first reviewer model; write `"rater": false` in the settings file to keep
  the reviewers' own levels.
- `/pr-deep` stays off when it was off, also when only some of its three
  models were set.
- `workflow.shardFindings` and the documentation-only `models._help` are
  removed. Every other setting keeps its value. The update repairs nothing:
  a value 0.4.x could not use, or a setting this version does not know,
  stays as it is, and `/pr-setup` names it afterwards. A mode whose models
  already name `reviewers` stays as it is; where it is written as this
  version writes a mode, `/pr-setup` shows the passes it will run.
- **If `afterReview` is `publish` for a mode**, the comments of new reviews
  are posted automatically as before, although no verifier confirmed their
  findings. `/pr-setup` names this before you confirm; set `afterReview` to
  `preview` for that mode if you want to read the comments first.

For a source installation, extract the new archive and run its installer with
`--replace`:

```sh
sh install.sh --config-dir /absolute/path/to/v2-opencode-config --replace
```

The installer carries a settings file of 0.4.x over byte for byte and says so;
update it with `/pr-setup` as above. Manual copying needs 33 files now (four
prompt files went, one came); the
[README lists them](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.0/README.md#manual-copying-without-git).

## Compatibility and validation

The tested target is OpenCode CLI **2.3.2** (V2 plugin API), Node.js
**22.23.3**, Ubuntu **22.04.5** under WSL2, and Azure DevOps Services REST API
**7.1**. `/pr-check` warns on other OpenCode versions. OpenCode 1.x and Azure
DevOps Server are not supported; other operating systems remain unvalidated.

The private agents are now `azpr-<mode>-reviewer`, `-reviewerb`, `-reviewerc`,
`-reviewerd`, `-dedupe`, `-rating` and `-comment-plan`, plus
`-comment-plan-verified` for the reviews that 0.4.x saved.

The
[validation record](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.5.0/docs/VALIDATION.md#050-release-candidate-acceptance-2026-11-23)
lists the offline checks, the checks on a real OpenCode 2.3.2 host with fake
services (among them an update of a settings file of 0.4.6 in the terminal
UI), and the runs with real models.

The npm package, Git package and source archive contain the same runtime, with
no npm dependencies or install scripts; the source archive also contains the
documentation, installers and settings example. The release source artifact is
`opencode-azure-devops-pr-review-v2-0.5.0.tar.gz`, with checksums in `SHA256SUMS`.
