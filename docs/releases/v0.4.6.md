# Azure DevOps PR Review for OpenCode — 0.4.6

One defect that a pull request makes at several places now gets one inline
comment that lists the other places, where each place had a thread of its
own. The reviewer and verifier instructions are those of 0.4.5, so a review
finds and verifies as before; the comment planner's instructions changed, and
no setting is new.

## What changed

- **One comment for one defect at several places.** A mistake repeated in a
  pull request (the same wrong call in each handler, the same stale text in
  each copy) is one finding per place, because each place needs its own
  correction. Each of them used to get an inline thread with much the same
  text. The comment planner may now write one comment for such findings, at
  the place that shows the mistake most clearly.
- **Every other place is listed under it.** AZPR adds the list itself, from
  the findings' own locations:

  ```text
  **📍 Also at** (the same defect; fix these places with it):
  - `/src/orders/refund.ts:41-44` (F-3)
  - `/src/orders/cancel.ts:18` (F-5)
  ```

  In Chinese the heading is `**📍 其他位置**`. The list is plain text: nothing
  is collapsed or linked, so its own markup holds nothing back in automatic
  publication (a file name is checked like any other text of the comment).
  Azure DevOps cannot anchor one thread at several places, which is why the
  places are written out.
- **Only for the same defect.** Findings share a comment only when they have
  the same severity (high or medium), lie on different lines of files the
  pull request changes, and the planner says they are the same mistake with
  the same correction. Places that need different corrections keep their own
  comments, and when unsure the planner keeps findings apart. The preview
  shows a shared comment with all its findings and the planner's reason
  (`Combined: …`), so with a preview you see it before anything is posted
  (automatic publication, `afterReview: publish` or `--publish` after the PR
  URL, posts such a comment like any other). A place is
  listed as its finding states it, so only a finding whose lines the file
  has at the reviewed commit can be one of several places, and the comment's
  anchor must touch the lines of exactly one of its findings.
- **The review keeps every finding.** It still has one finding per place.
  Each keeps its row in the summary index and its ID, and you can leave one
  out or change its severity after a preview like any finding; the next
  preview then lists the places that are left.
- **One more planner stage on larger reviews.** Which findings may be such
  repeats is settled before the planning pages are made, and only when at
  least two high or medium findings of one severity lie at different places.
  When all findings fit one page (at most four, within a page's text), no
  session is added: that page is offered those findings. Otherwise, where
  two of them fit one page together, a grouping pass runs first: one more
  stage of the comment planner's model, usually one request, whose input is
  those findings and which says which are one mistake at several places. If
  it fails, a progress notice says so and every finding gets its own
  comment, as before.
- **Two markers, so that "already there" is exact.** Every inline comment
  ends with a hidden marker made of its file and the lines it quotes, and
  publication skips a comment whose marker the pull request already has. A
  shared comment carries that marker of its place, so that a later comment
  on those lines finds it, and a second one of its own, made of the place
  and the other places it lists. It is skipped only when its own marker is
  there: `ALREADY_PRESENT` then means this very comment, with every place.
  The markers of comments for one place are unchanged.
- **No second thread on the same lines.** A shared comment does not find a
  comment for one place (a thread per place that an earlier version posted,
  say), so it would be posted next to it. When planning, a shared comment on
  lines that already carry a comment of AZPR's is sent back, and the planner
  is asked to put it at another of its places or to leave that finding out;
  one that still stands there is dropped, and the preview says why.

Nothing posted is ever changed, and an item the PR already has is skipped as
always. When a pull request with a shared comment is planned again, the
planner is told which other places that thread covers. See
[one defect at several places](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.4.6/docs/COMMENTING.md#one-defect-at-several-places).

The README's benchmark section also says now what each precision measures:
the share of comments on Martian's list of issues, next to the share of
findings that ReviewBench's judge rated valid.

## Installation

```sh
opencode plugin add opencode-azure-devops-pr-review@0.4.6
```

Alternatively, install the same release from Git:

```sh
opencode plugin add 'github:WTLAIB/opencode-azure-devops-pr-review-v2#v0.4.6'
```

Add only one of them. Then open OpenCode's terminal UI and type `/pr-setup`;
the
[quickstart](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.4.6/docs/QUICKSTART.md)
walks through it, with a recording of the dialogs, and shows the way without
the terminal UI.

## Upgrading AZPR

For an entry that `opencode plugin add` created, add 0.4.6 and remove the
previous version only when the download succeeded. Replace `PREVIOUS_VERSION`
with the version in your `plugins` entry, such as 0.4.5:

```sh
opencode plugin add opencode-azure-devops-pr-review@0.4.6 &&
  opencode plugin remove opencode-azure-devops-pr-review@PREVIOUS_VERSION
```

Run them when no AZPR command is running. Running only the first command
leaves the previous version running. For an entry with options, change only
its `package` value; the OpenCode service then downloads 0.4.6 with its own
network settings. See
[upgrading](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.4.6/README.md#upgrading)
for the details. External settings, the PAT file and review records remain in
place, and no setting is new or required. A preview that 0.4.5 saved is
posted as it was saved; plan it again (`/pr-comment`) to get shared comments.

For a source installation, extract the new archive and run its installer with
`--replace` to retain settings:

```sh
sh install.sh --config-dir /absolute/path/to/v2-opencode-config --replace
```

Manual copying needs the same 36 files as 0.4.5.

## Compatibility and validation

The tested target is OpenCode CLI **2.3.0** (V2 plugin API), Node.js
**22.23.3**, Ubuntu **22.04.5** under WSL2, and Azure DevOps Services REST API
**7.1**. OpenCode 1.x and Azure DevOps Server are not supported; other operating
systems remain unvalidated.

Of the prompts under `src/prompts`, the two of the comment planner changed
(`comment-plan.md`, `comment-policy.md`); the reviewers', the verifier's, the
duplicate check's and the rating's are those of 0.4.5, so reviews run, find
and verify as before. The
[validation record](https://github.com/WTLAIB/opencode-azure-devops-pr-review-v2/blob/v0.4.6/docs/VALIDATION.md#046-release-candidate-acceptance-2026-11-21)
lists the offline checks and the checks on a real OpenCode host with fake
services: a review of 120 files whose grouping pass found one defect in three
files, which then shared a page, one comment and one thread on the fake Azure
DevOps, with the two other places listed in it.

The npm package, Git package and source archive contain the same runtime, with
no npm dependencies or install scripts; the source archive also contains the
documentation, installers and settings example. The release source artifact is
`opencode-azure-devops-pr-review-v2-0.4.6.tar.gz`, with checksums in `SHA256SUMS`.
